# تغيير الراتب وتاريخ تطبيقه من الملف والطلب — 13 سبتمبر 2026

يكمل هذا المسار توثيق السريان في ح4 من القسم1 وPL-04، بعد موافقة المالك على ربطه بتعديل الراتب المعتاد. يعتمد على جدولي ترحيل011 الموجودين، دون جدول أو ترحيل جديد. لا يغيّر حساب المسير الحالي إلى محرك السياسات، ولا ينشئ فروقات عن الفترات السابقة.

## تعديل ملف الموظف

`GET /api/employees/:id/salary-change-context` يحتاج `employees.edit` ونطاق الموظف نفسه. يعيد `employeeId,current,historyRevision,currentSourceHash`؛ القيم الستة داخل `current` نصوص SQL دقيقة أو `null` والعملة كما هي. القراءة في معاملة `SERIALIZABLE` وقفل مالي مشترك. ترحيل السجل المفقود يعيد409، ولا يتحول إلى تاريخ فارغ.

`PATCH /api/employees/:id` يرسل تغيير الأجر الحقيقي في `salaryChange` وحدها:

```json
{
  "salaryChange": {
    "expectedRevision": 0,
    "expectedCurrentSourceHash": "<بصمة السياق المكونة من64حرفًا>",
    "effectiveDate": "2026-06-16",
    "reason": "قرار تعديل الراتب",
    "evidenceReference": "قرار الموارد البشرية123",
    "previousEffectiveFrom": "2026-06-01",
    "salary": {
      "basicSalary": "9000.00",
      "housingAllowance": "0.00",
      "transportAllowance": "0.00",
      "phoneAllowance": "0.00",
      "workNatureAllowance": "0.00",
      "otherAllowance": "0.00",
      "currency": "EGP"
    }
  }
}
```

السبب والمرجع وتاريخ السريان والمكونات الستة والعملة إلزامية عند تغيير الأجر. لا تحويل للمبلغ عبر `Number`؛ حدSQLهو `decimal(18,2)` وتُرفض كسور القروش والقيم السالبة والقيم الناقصة. `null` لا يساوي صفرًا. تغيير العملة تغيير مالي صريح ولا يحوّل مبالغها تلقائيًا.

تاريخ تعديل الملف يقبل اليوم أو الماضي. بداية الأجر السابق `previousEffectiveFrom` اختيارية، وتُقبل لأول سجل فقط وقبل تاريخ التغيير، بإقرار المستخدم بأن المستند يثبت القيم الحالية خلال تلك المدة. غيابها يبقي الفترة السابقة مجهولة؛ لا افتراض لتاريخ التعيين أو إعادة ملء من بيانات الموظف.

داخل معاملة التعديل نفسها: قفل الحضور المعتاد ثم القفل المالي للموظف، إعادة فحص النطاق، مقارنة المراجعة والبصمة، بناء الفترة الجديدة، فحص الفترات المغلقة، حفظ القيم الحالية الدقيقة ومراجعة السريان وسجل المكونات المتغيرة باسم المستخدم. فشل حفظ التاريخ أو ربط مرفق لاحق يرجع الأجر والتاريخ والتدقيق والبيانات المصاحبة معًا. لا سجلات مالية أو مسيرات تُنشأ.

تُحفظ الفترات والقرارات التالية كما هي. إذا كان التعديل يخص فترة قديمة قبل قرار لاحق، يبقى الأجر الحالي مساويًا للفترة السارية اليوم؛ لا يُستبدل تلقائيًا بقيمة الفترة القديمة. وجود فجوة تمنع إثبات أجر اليوم يوقف التطبيق. إعادة نفس الفترة بعد تحديث السياق لا تكرر المراجعة أو التدقيق.

المسير `APPROVED/PAID` ذو بند للموظف أو عضوية مضمنة يمنع التغيير المتداخل؛ العضوية التاريخية `NULL` تُعامل كمضمنة. العضو المستبعد بلا بند لا يمنع. التصفية `SETTLED/CLOSED` تمنع تعديل أجر الخدمة المغلقة من تاريخ يقع قبل نهاية خدمتها. هذه رسالة حاجة لمسار الفروقات، وليست إنشاء ذلك المسار.

التعديل غير المالي يحذف حقول الأجر والعملة من الحمولة. الخادم يحتفظ بتوافق الحمولة القديمة عندما تكون قيمها المالية مطابقة للمصدر فقط، ويرفض أي تغيير حقيقي دون بيانات السريان. يحفظ بقية الأعمدة المرسلة وحدها، فلا تعاد كتابة مبالغ الموظف المقروءة كأرقام عند تغيير الهاتف أو القسم. يتواصل التعديل غير المالي إذا تعذر تحميل سياق الأجر، بينما تُعطل حقول الأجر في الشاشة.

## طلب زيادة الراتب

النوع ذو الوجهة `salary_update_history` يتطلب `newSalary` نصيًا و`effectiveDate` و`reason`. يضاف ذلك إلى وصف النموذج وقت القراءة دون إعادة بذر الكتالوج أو استبدال سلاسل العميل. الحقول الإضافية المخصصة تبقى متاحة. نسبة الزيادة تأتي من الأساسي الحالي المقفل والراتب المطلوب؛ `increase_pct` المرسلة من العميل لا تحدد سلسلة الاعتماد. الأساسي يجب أن يكون موجبًا والجديد أكبر منه.

عند التقديم يحفظ الخادم داخل الطلب أساسًا يشمل الهوية والفرع ومكونات الأجر والعملة ومراجعة التاريخ وبصمة المصدر ومقدم الطلب، مع بصمة تشمل المبلغ والتاريخ والسبب. لا يقبل هذا الأساس أو هوية المعتمد من العميل. إعادة التقديم تُنشئ أساسًا جديدًا وتعيد حساب السلسلة.

الاعتماد النهائي لزيادة مستحقة يطبق الكاتب المشترك داخل نفس المعاملة. إذا كان التاريخ مستقبلًا يصبح الطلب `IN_EXECUTION` ويحتفظ بمرجع اعتماده، دون تعديل الأجر الحالي أو إنشاء فترة مبكرة. منفذ الطلبات اليومي ولحاق الإقلاع ينفذانه عند حلول التاريخ، بعد إعادة فحص المصدر والتاريخ والفرع ونشاط الموظف. لا جدول جديد للمواعيد؛ الطلب نفسه يحتفظ بالموعد.

تغيير المصدر منذ التقديم يمنع تنفيذ زيادة وفق دليل قديم. التنفيذ المكتمل لا يتكرر. هوية التدقيق من موافقة دورة الطلب الحالية أو سياق التنفيذ الفوري الصريح؛ لا ينسب زيادة جديدة لموافقة سبقت إرجاع الطلب لاستكمال المعلومات.

إذا تعذّر تنفيذ القرار المؤجل، تستطيع الإدارة صاحبة `settings.manage` داخل فرع الطلب إغلاقه بالرفض بسبب موثق، ثم تقديم قرار جديد. يستخدم ذلك `POST /api/requests/:id/reject-execution` بعد القفل المالي وقفل الطلب. وجود مراجعة أجر أو حركة موظف مرتبطة بالطلب يمنع الرفض؛ لا يُعكس أجر منفذ. الاستثناء محصور بطلب الأجر، ولا يوسع انتقال `IN_EXECUTION` العام لباقي الوجهات. زر الإغلاق في تفاصيل لوحة الطلبات الإدارية، وليس طلبات الموظف وحدها.

الطلب القديم غير المكتمل بلا تاريخ أو دليل لا يُعتمد بموعد مفترض؛ يُرجع لاستكمال المعلومات وإعادة التقديم. الطلبات التاريخية المكتملة لا تُعدل. الزيادة المؤجلة هنا تخص الأساسي؛ جدولة تعديلات البدلات الدائمة وكامل كتالوجها تبقى ضمن دفعتها.

## حدود الإغلاق

المسار المستقل `/payroll/salary-history` يبقى لإثبات أو تصحيح التاريخ بصلاحية `payroll.approve`، ويحافظ على عقده السابق: لا يغير أجر الملف ولا يولد فروقات. يعاد استخدام كاتب المراجعات بينه وبين التعديل المؤرخ، دون تغيير صلاحياته.

إنشاء موظف جديد يحتفظ بمساره الحالي؛ لا يولد تاريخ أجر افتراضيًا. تقويم أيام العمل التاريخي وأدلة الحضور والإسناد ولقطة المسير علىSQL والفروقات الرجعية وبوابة التكافؤ والظل ما زالت مستقلة ومطلوبة. تثبيت هذه الشاشات على المراجعة يتطلب الترحيلات والبناء المذكورين في دليل التشغيل؛ نجاح الاختبار المعزول لا يعني تحميل التحديث على خدمة المراجعة.
