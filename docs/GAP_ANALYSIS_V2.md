## 1. الأساس المفقود: الفروع + الصلاحيات المُقيّدة (Multi-Branch RBAC)

> **هذا هو حجر الأساس. يجب حلّه أولاً لأنه يمسّ كل الموديولات الأخرى (كل بيانات النظام يجب أن تُفلتر بالفرع).**

### الموجود حالياً
- الفروع موجودة كـ CRUD في `settings/branches` — لكن **مدير الفرع مجرد نص حر** غير مربوط بحساب مستخدم.
- `branch_id` موجود كعمود في `employees` و `departments` في الـ Schema — لكنه **غير مستغَل** (الفرع يُخزَّن كاسم نصي في الواجهة).
- RBAC موجود: أدوار (`roles`) + مصفوفة صلاحيات (`settings/roles`) بصيغة `module:action`.
- `role_permissions.scope` يدعم `all | team | self` فقط.

### الناقص (الحرج)
1. **`users` لا يحتوي `branch_id`** — لا يمكن ربط مستخدم بفرع أصلاً. هذا الحاجز الأكبر.
2. **لا قيمة `branch` في نطاق الصلاحيات** — لا يمكن قول "مدير HR لفرع المعادي يرى موظفي المعادي فقط".
3. **لا علم Super-Admin صريح** يميّز "المدير من فوق يرى الكل" عن "مدير فرع مقيّد".
4. **لا فلتر فرع** في قوائم الموظفين/الحضور/الرواتب/الإجازات.
5. **لا Branch Switcher** في الهيدر، ولا حقل فرع في نافذة إضافة المستخدم.
6. **الجداول التشغيلية غير مُقيّدة بفرع** (`payroll_periods` مثلاً `UNIQUE(company_id, month, year)` — يمنع مسيراً منفصلاً لكل فرع).

### المطلوب بناؤه
```
users.access_scope        → all_branches | own_branch | assigned_branches
user_branches (M:N)       → user_id, branch_id   (لدعم مسؤول عدة فروع)
roles.is_cross_branch     → علم صريح لتجاوز فلتر الفرع (super-admin)
role_permissions.scope    → إضافة 'branch' (و 'department')
branches.manager_user_id  → ربط مدير الفرع بحساب مستخدم حقيقي
```
- **فرض العزل في طبقة البيانات**: كل استعلام يُفلتر تلقائياً بفروع المستخدم (Row-Level Security في PostgreSQL أو query-scoping إجباري)، ما لم يكن `is_cross_branch`.
- إضافة `branch_id` لـ `payroll_periods` وإزالة قيد UNIQUE الحالي.
- UI: فلتر فرع موحّد + حقل الفرع في المستخدم + محدّد نطاق في الأدوار + Branch Switcher.

**النتيجة المطلوبة:** كل فرع مقفول ببياناته وموظفيه ومسيراته؛ المستخدم المُسنَد لفرع لا يرى غيره؛ الأدمن العام يرى الكل.

## 2. محرّك الطلبات والاعتمادات (Requests & Approval Engine)

> **العمود الفقري الثاني.** كل الطلبات (إجازة، إذن، إضافي، عهدة، استقالة، تصفية، تغيير بيانات…) يجب أن تمر عبره.

### الموجود حالياً
- **شاشة محرّك اعتمادات عام قابل للتهيئة** في `settings/approvals` — جيدة كنقطة بداية:
  - بناء سلسلة موافقات متعددة الخطوات (step 1 → 2 → 3).
  - أنواع معتمِدين: مدير مباشر، رئيس قسم، مدير HR، مدير مالي، مدير عام، شخص محدد، صلاحية محددة.
  - مهلة رد لكل خطوة + تفويض + موافقة تلقائية عند المهلة.
  - 10 أنواع طلبات مُعرّفة + بنية شروط تفرّع (conditions).

### الناقص
1. **غير موصول بأي backend** ولا بنماذج التقديم (طلب الإجازة يعمل `console.log` فقط).
2. **لا يوجد نموذج طلب مركزي (Generic Request)** بحالة موحّدة وسجل تدقيق.
3. **لا محرّك تنفيذ (Runtime)**: لا "خطوة حالية"، لا سجل موافقات، لا تصعيد/تفويض فعلي.
4. **محرّر الشروط غائب من الواجهة** (يُعرض ولا يُحرَّر).
5. لا يدعم: موافقة متوازية، نِصاب (AND/OR)، إعادة توجيه (rework)، سحب الطلب (withdraw).
6. **لا صندوق وارد موافقات موحّد** (فقط widget ثابت بـ 4 عناصر على الداشبورد).

### المطلوب بناؤه
```
requests               → id, type, requester_id, branch_id, status
                         (draft|pending|approved|rejected|withdrawn|completed),
                         payload (JSON), current_step, created_at
request_approvals      → request_id, step, approver_id, action, comment, acted_at
```
- محرّك تنفيذ يقرأ مسار الاعتماد المُهيّأ ويحرّك الطلب خطوة بخطوة.
- ربط كل نماذج التقديم بالمحرّك.
- صندوق وارد موافقات موحّد فعّال + صفحة "طلباتي".

## 3. استهداف ورؤية الطلبات (Request Targeting & Visibility) — فجوة كاملة

> طلبك: بعض الطلبات تظهر للكل، وبعضها لناس محددين (موظف/فريق/قسم/مشرف/فرع).

### الموجود حالياً
- **لا شيء.** كل النماذج متاحة للجميع عبر الروابط. الصلاحيات تتحكم في *من يرى الموديول* فقط، وليس *أي طلب يظهر لأي موظف*.

### المطلوب بناؤه
```
request_type_audience  → request_type_id + target_type (all|employee|team|
```

- ربط جمهور الطلب بالهيكل التنظيمي الموجود (branch/department/team/grade/job-title).

## 4. الحضور والجدول الأسبوعي والتأخير

### 4.1 الجدول الأسبوعي — أخطر فجوة تشغيلية
**الموجود:** الجدول مُنمذَج بأسماء أيام مجردة (`sunday/monday…`) **بلا تواريخ فعلية**؛ التنقل بين الأسابيع يغيّر الأرقام المعروضة فقط بينما محتوى الورديات ثابت. زر الحفظ/النسخ مجرد `alert()`.
**الناقص:**
- الجدول غير مربوط بأي تاريخ حقيقي — مستحيل معرفة "هذا الأحد تابع لأي أسبوع".
- لا مفهوم أسبوع-من-الشهر ولا ربط بتاريخ.
- `shift_assignments` الحالي (موظف→وردية واحدة بفترة) **لا يكفي** لتخزين جدول متغيّر لكل يوم.
- استثناء "آخر سبت في الشهر" مجرد نص يدوي غير محسوب.

**المطلوب:**
```
weekly_schedule_entries → employee_id + date + shift_id   (مؤرَّخ فعلياً)
```
+ محرك قواعد للاستثناءات المحسوبة + تفعيل الحفظ والنسخ.

### 4.2 احتساب التأخير
**الموجود:** حالة "متأخر" قيمة ثابتة مكتوبة يدوياً، لا تُحسب. لا ربط بين الحضور والوردية.
**الناقص:** لا يوجد أي منطق يقارن وقت البصمة الفعلي ببداية وردية اليوم المخصصة (مع فترة السماح).
**السيناريو المطلوب:** أسبوع الوردية 10:00 + حضور 10:25 = تأخير 25د؛ أسبوع الوردية 11:00 + حضور 10:50 = ملتزم. **غير مدعوم إطلاقاً** لأن الجدول لا يخزّن أوقاتاً حسب التاريخ.

### 4.3 أيام العمل مقابل ساعات العمل
**الناقص:** لا فصل واضح بين "الأيام التي يجب حضورها" (أيام الدوام) و"أوقات الوردية". `shifts.work_days` موجود في الـ Schema لكن **الواجهة لا تعرضه ولا تحرّره**. لا دعم لقاعدة "كل الأسبوع عدا الجمعة + آخر سبت".

### 4.4 التقرير الشهري لكل موظف
**الموجود:** صف مجمّع واحد لكل موظف بأرقام إجمالية فقط.
**الناقص:** لا كشف يومي يعرض كل أيام الشهر يوماً بيوم، مع تمييز الأيام الماضية (حضور/تأخير/غياب فعلي) عن الأيام القادمة ("لم يحن بعد") بناءً على تاريخ اليوم.

### 4.5 العمل الإضافي (Overtime)
**الناقص:** لا دورة اعتماد متعددة المستويات (مستوى واحد فقط). لا إعداد عتبة ("لو تجاوز X ساعة → يُوجَّه للاعتماد قبل احتسابه في الراتب"). لا ربط تلقائي بالرواتب. لا احتساب تلقائي من سجل الحضور.

### 4.6 الاستئذان (Permissions)
**الناقص:** أنواع الأذونات مثبّتة في الكود (لا `permission_types`). لا إعدادات لكل نوع (مدفوع؟/موافقة؟/حد أقصى). لا حد شهري. **لا منطق خصم عند تجاوز مدة الإذن** (أخذ ساعتين وعاد بعد 3 → خصم الساعة الزائدة). لا ربط بإلغاء تأخير اليوم عند وجود إذن معتمد.

## 5. الرواتب (Payroll)

### الموجود
- مبدّل نوع فترة (شهري/مخصص) + حقول من/إلى (لمرة واحدة على الشاشة فقط).
- شريط خطوات عرضي (جمع→حساب→مراجعة→اعتماد→صرف) غير تفاعلي.
- دالة إزالة خصم (سلفة/غياب) — محلية فقط، لا تُحفظ.

### الناقص
1. **لا إعداد لدورة رواتب متكررة مخصّصة** (مثل 23→22). لا عمود cut-off day في `payroll_periods`.
2. **مسير الرواتب غير مربوط بدورة اعتماد فعلية**؛ "مسير الرواتب" ليس نوعاً في محرّك الاعتمادات.
3. **لا مسير منفصل لكل فرع** (`payroll_periods` بلا `branch_id`).
4. **إزالة الخصم محلية لا تُحفظ** وتقتصر على نوعين ثابتين؛ لا سبب/مدقّق/سجل.
5. لا توليد فعلي لملفات WPS/GOSI/البنك.

### المطلوب
- إعداد دورة رواتب (anchor day) على مستوى الشركة/الفرع.
- كيان "مسير رواتب" بدورة حالة فعلية + اعتماد متعدد المستويات + `branch_id`.
- إدارة خصومات ديناميكية قابلة للإلغاء/التعليق قبل قفل المسير مع سبب وسجل تدقيق.

## 6. الإجازات (Leaves) — الرصيد المُرحّل

### الموجود
- `leave_balances` به `carried_over` كرقم للعرض فقط. أنواع الإجازات بها حد ترحيل. شاشة إضافة موظف بها قواعد استحقاق (شهري/سنوي) وبداية الاستحقاق.

### الناقص (طلبك بالظبط)
1. **لا حقل لإدخال رصيد افتتاحي/مُرحّل يدوياً** عند إضافة موظف قائم (مثلاً عنده أصلاً 15 يوم).
2. **لا تاريخ انتهاء (expiry) للرصيد القديم** (ساري حتى نهاية السنة / تاريخ محدد / بلا انتهاء).
3. **لا فصل بين "الرصيد القديم المُرحّل" و"الرصيد الجديد المتراكم من تاريخ الالتحاق"** — النموذج رصيد سنوي واحد بلا طبقات ولا محرّك تراكم فعلي.
4. لا مهمة ترحيل سنوي تلقائي.

### المطلوب
```
leave_balances → إضافة: opening_balance, opening_expiry_date,
                 accrued_balance (يُحسب من join_date)، مع فصل الطبقتين
```
+ محرّك تراكم (accrual job) + منطق ترحيل سنوي مع الحد والانتهاء.

## 7. العهد (Custody / Assets) — غائب بالكامل

**مؤكَّد: لا يوجد نظام عهد.** فقط عرض ثابت في صفحة الموظف وقائمة ثابتة داخل إنهاء الخدمة.

### المطلوب (النظام كامل)
```
asset_types    → أنواع العهد (لابتوب/موبايل/سيارة…), requires_approval,
                 approval_workflow_id, depreciation_rate
employee_assets→ سجل تخصيص عهدة لموظف: asset_type, serial, assigned_date,
                 status (assigned|returned|lost|damaged), value
```
- تخصيص عهدة عند إضافة/تعديل الموظف (checkbox + تاريخ) — مع خيار دورة اعتماد للتسليم.
- **إرجاع/تحرير عهدة** مستقل (خارج إنهاء الخدمة) بدورة اعتماد (موظف ← مدير ← HR ← فحص).
- ربط تلف/فقد العهدة تلقائياً بخصومات المسير والتصفية.

## 8. الاستقالة وتصفية المستحقات (Resignation & Final Settlement)

### الموجود
- شاشة تصفية تفصيلية (مكافأة نهاية الخدمة م.84 + بدل إجازات − سلف − تأمينات) + معالج إنهاء خدمة إداري (5 خطوات).

### الناقص
1. **لا يوجد نموذج استقالة يقدّمه الموظف بنفسه** (موجود إداري من HR فقط). يجب أن يظهر في صندوق موافقات: المدير المباشر ← HR ← الإدارة، وبعد الاعتماد وفترة الإشعار → أرشفة الموظف.
2. **"اعتماد التصفية" مجرد خطوة واحدة محلية** — يجب دورة اعتماد حقيقية (مدير مالي ← HR ← مدير عام) مربوطة بالمحرّك، **تنتهي بإشعار/إقرار الموظف على المخالصة**.
3. **لا جدول قاعدة بيانات للتصفية** (`settlements`) — لا حفظ ولا سجل تدقيق.
4. حساب مكافأة نهاية الخدمة مكرر ومختلف بين شاشتين — يحتاج مصدر حساب موحّد.
5. بدل الإجازات يعتمد على رقم ثابت لا على الرصيد الفعلي (مرتبط بفجوة الإجازات).

## 9. الخدمة الذاتية وأنواع الطلبات الناقصة

### الناقص
- **لا صفحة "طلباتي"** (My Requests) لمتابعة حالة/تاريخ الطلبات — غائبة نهائياً.
- **لا بوابة خدمة ذاتية موحّدة (ESS)** تجمع كل ما يمكن للموظف تقديمه.
- **تعديل الملف الشخصي معطّل** — ولا يوجد **"طلب تغيير بيانات"** يمر باعتماد HR.

### أنواع طلبات ناقصة (تحتاج نموذج + مسار اعتماد + صندوق وارد)
استقالة (ذاتية) · طلب تغيير بيانات · سلفة · مصاريف · رحلة عمل · طلب شهادة/تعريف بالراتب · طلب عهدة/أصل · عمل عن بُعد · شكوى/تظلّم · تظلّم على خصم · تغيير وردية.

### موديولات إضافية لنظام عالمي (اختيارية/مرحلة لاحقة)
Onboarding (checklists) · Offboarding كامل · إدارة المصاريف · مكتب مساعدة/تذاكر HR · الاستبيانات والاندماج · المزايا · التعاقب والمسار المهني · LMS فعلي.

## 10. ترتيب البناء المقترح (Build Order)

عشان تبني بترتيب صحيح ومتقفلش السيكل مرتين:

**المرحلة 1 — الأساس (Foundation):**
1. نموذج البيانات الأساسي + `company_id`/`branch_id` في كل الجداول.
2. **Multi-Branch RBAC** (users↔branches, scope=branch, is_cross_branch, فرض العزل).
3. المصادقة والجلسات + فرض الصلاحيات على كل API.

**المرحلة 2 — العمود الفقري (Backbone):**
4. **محرّك الطلبات + الاعتمادات** (Generic Request + Runtime) موصول بمحرّك `settings/approvals` الموجود.
5. **استهداف الطلبات** (audience + eligibility).
6. **الإشعارات** (Notification Service) موصولة بالأحداث.
7. **صندوق "طلباتي" + صندوق وارد الموافقات**.

**المرحلة 3 — الموديولات التشغيلية:**
8. الحضور: جدول أسبوعي مؤرَّخ + محرّك تأخير + تقرير شهري يومي.
9. الإجازات: رصيد افتتاحي بصلاحية + طبقات + تراكم.
10. الرواتب: دورة مخصّصة + مسير لكل فرع + اعتماد + خصومات ديناميكية.
11. العهد: النظام كامل.
12. الاستقالة + التصفية: تقديم ذاتي + دورة اعتماد + إشعار الموظف.
