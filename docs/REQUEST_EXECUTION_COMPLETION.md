## ضوابط التنفيذ

- الوجهات الثلاث الجديدة لا تقبل أكواد أنواع غير متوافقة معها.
- الموظفون غير الموجودين أو غير النشطين لا ينتجون نجاحاً وهمياً في المسارات الجديدة.
- مبادلة الوردية ترفض نفس الموظف، واختلاف الفرع، والإجازة المعتمدة، والورديات المتطابقة أو غير الصالحة، وطلب مبادلة آخر يمس أحد الموظفين في التاريخ نفسه.
- مبادلة الوردية تعمل داخل الفرع نفسه؛ نقل الموظف إلى فرع آخر متاح لمنشئ طلب من دور `super_admin` فقط.
- حقول العقود والمسمى والمبادلة تظهر في الكتالوج عند القراءة للنسخ القديمة دون إعادة seed أو الكتابة فوق تخصيصات المستخدم.
- قفل الطلب قبل التنفيذ يمنع تكرار تنفيذ موافقتين متزامنتين بعد اكتمال الطلب أو دخوله التنفيذ المؤجل.

### EMP-14 التجديد المباشر

أضيف `RenewEmployeeContractDto` ومسار `POST /employees/:id/contract/renew` بصلاحية `employees.edit` ونطاق الفرع. `EmployeesService.renewContract` يقفل الموظف ويمنع تجديد من انتهت خدمته والعقد الدائم والتواريخ المستحيلة أو المتداخلة ووجود طلب عقد قيد المعالجة. التجديد يبدأ بعد نهاية العقد الحالي، ويحافظ على joinDate وحالة الموظف. التواريخ مصدر المدة؛ لا تُحمل مدة العقد القديمة إلى الجديد.

`contractFileRef` اختياري ومحصور في `file:N`، ويُربط بواسطة `linkEmployeeFiles` داخل نفس المعاملة. يُنشأ `EmployeeDocument` بنوع contract وتاريخي التجديد، ويُكتب سجل old/new dates وactor user ID والسبب ومرجع الملف. اختبار فشل بعد حفظ المستند أثبت تراجع الموظف وربط الملف والمستند والسجل معاً. الواجهة في contracts/page.tsx تعرض التاريخين والسبب وملفاً اختيارياً حتى 10MB، وتعيد استخدام مرجع الرفع عند إعادة محاولة الحفظ، وتعرض خطأ داخل النافذة ونجاحاً بعد استجابة المسار.

تنبيهات انتهاء العقود والمستندات من عمل الجذر تُشتق من البيانات الحالية عند GET /notifications، وتغطي أول قراءة بعد توقف الخدمة؛ لم ننشئ job يومية أو تنبيهات مخزنة. لا يوجد إنهاء خدمة تلقائي لمجرد انتهاء العقد؛ هذا قرار HR. المرجع المجمع للتنبيهات واختبارها: recovery.integration.cjs واختبار `expiry reminders derive from current scoped data and disappear after renewal`.

### NAM-1 توحيد فعل الاعتماد

أصبح ResolvedStep.action من نوع ApprovalAction، ويستخدم RequestsService.act قيمة واحدة للخطوة والسجل: APPROVED/REJECTED/RETURNED_FOR_INFO. فعل POST العام يبقى APPROVE/REJECT/RETURN للتوافق. normalizer في approval-actions.ts يقرأ الخطوات القديمة عبر تفاصيل الطلب وmine وall وinbox والمحرك دون تغيير السجل التاريخي أو كتابة خلال GET. مقارنات تقدم الطلب وكونسول الطلبات تقبل الصيغتين؛ الإرجاع لا يُعرض كاعتماد أخضر.

اختبارا NAM-1 ضمن آخر تشغيل **30/30 PASS** يثبتان التخزين الموحد للأفعال الثلاثة، والقراءة المتوافقة مع بقاء JSON وaudit كما هما في SQL، وإعادة تقديم طلب قديم ذي RETURN واعتماده مع الاحتفاظ بسجل الإرجاع. لا schema migration ولا UPDATE للسجل التاريخي مطلوبان لهذا الإصلاح. TypeScript للواجهة والباك ناجحان بعد آخر تعديل.

### EMP-12 إفراغ الحقول الاختيارية

المراجعة المحددة وجدت نقصاً حقيقياً في نماذج الفروع والأقسام والفرق: كانت حقول اختيارية تُرسل undefined عند التفريغ فتُحذف من JSON. تعديل السجل الآن يرسل null للاسم الإنجليزي والمدينة والعنوان والهاتف والبريد ومدير الفرع، وللاسم الإنجليزي وكود ومدير القسم، ولكود وقائد الفريق. حقول المستخدم (الفرع/الموظف) ونوع الإجازة (المرفق المطلوب/الحد الأقصى) كانت صحيحة بالفعل، ولم تُعدل. DTOs تستخدم IsOptional وhandlers تحفظ null؛ فُحص ذلك بالاختبار الحقيقي ولم تتطلب تغييراً.

آخر تشغيل للمجموعة: **31/31 PASS** في 26.95 ثانية. اختبار EMP-12 يملأ الحقول ثم يمسحها عبر PATCH ويعيد GET لكل جهة من الخمسة، ويتأكد من بقاء null، بما فيها الأب ومركز التكلفة والدولة وتجاوز العطلة. TypeScript للواجهة ناجح بعد تعديل النماذج الثلاثة. هذا تحقق API ومراجعة كود الواجهة، وليس ادعاء اختبار بصري لكل حقل.
